# Assumptions

This document explains the decisions behind the admission system. Each entry
lists the assumption and the reason for it.

## Data model

- **Class and shift are represented by one class record.** The assignment speaks
  of class-and-shift categories such as "Class 6 Morning" and "Class 6 Day".
  The API therefore treats each name as an independent admission category with
  its own seat capacity. No separate shift table is needed for the required
  behaviour.
- **Class IDs are opaque UUID-derived strings (`c_...`).** They are generated by
  the server, are not sequential, and do not expose database internals.
- **Hold IDs are opaque UUID-derived strings (`h_...`).** The assignment requires
  random identifiers, and random IDs avoid predictable enumeration.
- **Class names are free-form strings of at most 200 characters.** Leading and
  trailing whitespace is trimmed, and empty or whitespace-only names are
  rejected. The assignment does not define a fixed class list or naming scheme.
- **Total seats must be a positive integer.** The database enforces
  `total_seats > 0` and the API rejects zero, negative and non-integer values.
- **Status values are restricted to `HELD`, `CONFIRMED`, `EXPIRED` and
  `CANCELLED`.** A database check constraint enforces the same set.

## Time and expiration

- **All authoritative time comes from PostgreSQL.** Hold creation, expiration,
  confirmation and cancellation decisions use `clock_timestamp()`, so hosts with
  different clocks cannot disagree about whether a reservation is still valid.
- **Timestamps are stored with time zone (`timestamptz`) and returned in UTC.**
  The frontend formats them in the browser's local time zone for display.
- **A hold is valid while `current_time < expires_at`.** At or after
  `expires_at` it is expired. The conditional updates use
  `expires_at > clock_timestamp()`, which is the same boundary.
- **Expiration is automatic.** A `BackgroundService` in every backend instance
  periodically finds classes with overdue `HELD` rows, locks each class, and
  transitions that class's overdue rows to `EXPIRED`. The worker is safe when
  two instances run at the same time because it uses the same class advisory
  lock as the request handlers.
- **Expiration is also lazy inside relevant transactions.** Hold creation,
  confirmation and cancellation expire overdue holds for their class before
  deciding, so correctness does not depend on the worker's timing.
- **Seat counts exclude overdue holds even before the worker runs.** The class
  count query only counts `HELD` rows whose `expires_at` is in the future.
- **The default hold duration is 600 seconds.** It is configurable through
  `HOLD_DURATION_SECONDS` for demonstrations and tests.

## Seats, duplicates and applications

- **`heldSeats + confirmedSeats <= totalSeats` is a hard invariant.** It is
  enforced inside a PostgreSQL transaction while holding a class-level
  advisory lock. No application-side counter exists.
- **One active application per student per class.** A partial unique index on
  `(class_id, student_id)` where status is `HELD` or `CONFIRMED` enforces it,
  and the transactional duplicate check returns `409`.
- **Students may apply independently to different classes.** Each class has its
  own advisory-lock key and its own capacity.
- **Reapplication is allowed after cancellation or expiration.** Those states
  are excluded from the partial unique index, so the student may create a new
  hold; the old record remains for the application history.
- **Duplicate active applications are rejected with `409`.** This applies to
  both `HELD` and `CONFIRMED` applications.
- **A cancelled application cannot be confirmed.** Confirmation only changes a
  `HELD` row that has not reached its expiration boundary.
- **A confirmed application cannot be cancelled and confirmation is
  idempotent.** Repeated confirmation returns `200` without increasing the
  confirmed count. Once `CONFIRMED`, cancellation returns `409`.

## Concurrency

- **PostgreSQL transaction-scoped advisory locks are the coordination
  mechanism.** All state-changing operations for a class use
  `pg_advisory_xact_lock(hashtextextended(classId, 0))`. The lock is released
  automatically at transaction end and works across processes and hosts.
- **No in-memory locking is used for cross-request correctness.** Process-local
  state would not coordinate two backend instances.
- **The partial unique index is defence in depth.** Even if a future code path
  forgot the advisory lock, the index would still prevent duplicate active
  applications.
- **The background worker processes classes in batches.** It only selects
  classes that currently have overdue `HELD` rows and uses the partial expiry
  index, so it does not scan the entire history on every tick.

## Database and migrations

- **Schema initialization is versioned and lock-protected.** Migrations run
  behind a PostgreSQL session-level advisory lock. A second instance waits for
  the first to finish instead of racing on DDL.
- **Legacy schemas are upgraded in place.** Migration 2 adds audit columns that
  older versions of the schema did not have, so an existing `pgdata` volume is
  upgraded rather than discarded.
- **Relevant indexes exist.** There is a partial unique index for active
  applications, a partial expiry index for the worker, and indexes for
  class/status and student lookups.
- **Data is persisted in the named volume `pgdata`.** It survives container
  restarts and `docker compose down`/`up`; only `docker compose down -v` deletes
  it.

## Identity, privacy and security

- **`X-Student-Id` is identification, not authentication.** The assignment does
  not require a login system. The header prevents accidental cross-student
  operations and is used for ownership checks, but it cannot prove identity.
  Anyone who knows a registration number could impersonate that student.
- **Ownership is enforced for confirmation and cancellation.** A different
  student receives `403 Forbidden`; the hold is not modified.
- **The public hold-status endpoint does not expose the registration number.**
  `GET /holds/{holdId}` returns hold, class, status and expiration information
  only.
- **Registration numbers are not logged.** Logs contain HTTP method, path and
  non-personal class identifiers only. Error responses never contain database
  details or stack traces.
- **The administration create-class form is public.** No administrator role or
  authentication is specified by the assignment.

## Frontend

- **The selected student number is persisted in `localStorage`.** This satisfies
  browser-session persistence; a Clear button removes it.
- **Changing the student identity immediately clears the previous student's
  applications.** In-flight requests are aborted and a request-generation
  counter prevents a late response for the old identity from updating the new
  one.
- **The countdown is presentation only.** The UI shows `EXPIRED` when the local
  clock reaches the boundary and disables payment/cancellation, but the backend
  remains authoritative.
- **Class lists and applications refresh every three seconds.** Requests are
  deduplicated per generation and intervals are cleared on unmount and on
  identity changes.
- **The frontend API URL is a build-time setting (`VITE_API_URL`).** It is
  passed as a Docker build argument so the production bundle uses the intended
  endpoint.

## Deployment

- **Two backend instances run from the same image.** `backend1` publishes host
  port `8080` and `backend2` publishes `8081`; both listen on `8080` inside the
  container and share the same PostgreSQL database.
- **Both instances run the expiration worker.** This is intentional and safe;
  the class advisory locks serialize their work.
- **The frontend continues to use instance 1 by default.** `VITE_API_URL`
  defaults to `http://localhost:8080`; either instance can serve any request
  because all state is in PostgreSQL.
- **Docker is the only prerequisite for the evaluator.** Test-runner containers
  are provided so .NET and Node.js do not need to be installed on the host.
